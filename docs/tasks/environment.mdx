`environment/` 目录定义智能体和验证器的运行环境。该目录通常包含 `Dockerfile` 或 `docker-compose.yaml` 文件。

## Harbor（智能体评测框架） 中的环境是什么？ {#what-is-an-environment-in-harbor%3F}

Harbor（智能体评测框架）中的环境是 **`BaseEnvironment`** 的一种实现，其中定义了以下方法：`exec`、`upload_file`、`upload_dir`、`download_file`、`download_dir`、`start` 和 `stop`。

这些方法通常针对 [Docker（容器平台）](https://www.docker.com/) 等容器运行时，或 [Daytona（云沙箱平台）](https://www.daytona.io/) 和 [Modal（云计算与沙箱平台）](https://modal.com/) 等云端沙箱提供方实现。

## 预构建 Docker 镜像 {#prebuilt-docker-images}

用户可以预先构建 Docker 镜像，将其托管在 Docker Hub 或 GitHub（代码托管平台） Packages 等容器注册表中，并通过 `task.toml` 中的 `[environment].docker_image` 引用。若提供预构建镜像，大多数提供方会优先使用它，而不是从 `environment/` 目录构建，以提升速度和可复现性。

<Note>
  如果在 `task.toml` 中设置了 `[environment].docker_image`，可以完全省略 `environment/` 目录。
</Note>

## MCP（模型上下文协议） {#mcps}

Harbor 通过 `environment/docker-compose.yaml` 支持多容器环境。详情请参阅[多容器](/tasks/multi-container)。

MCP 通常用于模拟数据库或 API（应用程序接口） 等外部服务，可在 `docker-compose.yaml` 文件中作为服务实现。

应在 `task.toml` 中使用 `[[environment.mcp_servers]]` 声明可用的 MCP 服务器，以便[兼容的智能体](/agents/pre-integrated-agents#agent-capabilities)（例如 Claude Code（Anthropic 编程智能体）、Codex（OpenAI 编程智能体））自动注册这些服务器。

```toml title="task.toml"
[[environment.mcp_servers]]
name = "mcp-server"
transport = "streamable-http"
url = "http://mcp-server:8000/mcp"
headers = { Authorization = "Bearer ${MCP_TOKEN}" }
```

Claude Code 和 Codex 支持 `headers`。Codex 要求使用可流式 HTTP（超文本传输协议）。变量值支持 `${VAR}` 和 `${VAR:-default}`，并优先使用智能体环境变量（包括 `--ae`），之后才查找主机环境变量。任务请求头访问主机变量前，Harbor 会先询问。智能体服务器会覆盖同名的任务服务器。变量缺失或请求头不受支持时，会在设置阶段开始前报错。

凭据必须使用没有字面默认值的变量，例如 `Bearer ${TOKEN}` 或 `Basic ${USER}:${PASSWORD}`。Cookie 应使用 `${COOKIE}`，并在变量中提供完整的 Cookie 字符串。保存的配置会保留这些模板；解析后的凭据会从 Trial（单次运行） 输出中隐藏。

## 技能 {#skills}

可以将技能打包到环境中，并通过 `[environment].skills_dir` 提供给[兼容的智能体](/agents/pre-integrated-agents#agent-capabilities)。

```toml title="task.toml"
[environment]
skills_dir = "/app/skills"
```

所需目录结构、镜像配置以及 Harbor 如何向智能体传递技能，请参阅[任务 → 技能](/tasks/skills)。

## 工具 {#tools}

Harbor 将工具视为智能体的组成部分，而非环境的一部分。如果环境提供工具，应采用 MCP、技能、API 或 CLI（命令行界面） 的形式。

在 Harbor 中，智能体可以在环境内部或外部运行。如果智能体在环境内部运行，可以使用任意工具；如果在环境外部运行，则其工具必须由上文定义的 `BaseEnvironment` 基本操作组成。这些操作类似系统调用，因此通常不会过度限制智能体。

## 外部服务如何处理？ {#what-about-external-services%3F}

数据库或 API 等外部服务可以进行模拟，也可以直接使用。

例如，如果任务需要与 Stripe 交互，你可以在 `environment/docker-compose.yaml` 中将 Stripe 的一小部分功能模拟为服务，也可以直接调用真实的 Stripe API。对于已提供沙箱或开发模式的 Stripe 等产品，这种方式效果最佳。

我们建议尽可能在沙箱中运行外部服务，而不是直接调用它们，这样更便于控制并提高可复现性。

如果选择直接连接生产服务，可以考虑使用 `[agent].allowed_hosts` 将智能体的网络访问限制到该特定端点。

## 如果智能体和环境都是外部服务，怎么办？ {#what-if-my-agent-and-environment-are-external-services%3F}

生产环境中的智能体和环境常常是紧密耦合的产品（例如，调用工具的智能体与产品 API 紧密集成）。此时，你可能会考虑通过 Harbor 环境调用智能体 API 执行 Rollout，再调用环境 API 验证智能体输出。

如果你的使用方式属于这种情况，Harbor 可能不适合你的用例。

Harbor 适用于评测能够使用代码执行和文件系统的编程或协作智能体。我们认为，大多数智能体都在朝这个方向发展；现有产品公司也应评估编程智能体使用其 MCP、API 和 CLI 的能力，以及能否借助这些能力实现产品功能（例如从 W2 表单中提取字段）。

## 特殊路径 {#special-paths}

以下为 Linux（操作系统内核及相关系统） 路径（Windows（微软操作系统） 使用对应的 `C:` 路径）：

| 路径 | 说明 |
| ----------------- | ------------------------------------------------------------------ |
| `/logs/verifier/` | 奖励和验证器输出 |
| `/logs/agent/`    | 可选的智能体日志 |
| `/solution/`      | Oracle 将[解决方案](/tasks/solution)复制到此处 |
| `/tests/`         | 使用共享验证器时，Harness 会将[测试](/tasks/verifier)复制到此处 |

Trial 结束后，`/logs/` 会同步到主机，以便调试。

## 资源 {#resources}

在 `task.toml` 的 `[environment]` 部分声明资源。

```toml title="task.toml"
[environment]
cpus = 2
memory_mb = 4096
storage_mb = 10240
gpus = 1
gpu_types = ["H100", "A100"]

[environment.tpu]
type = "v6e"
topology = "2x4"
```

这些字段均为可选项。如果省略，Harbor 会使用提供方的默认资源配置。

Harbor 用户也可以使用 `--cpus` 和 `--memory` 参数指定提供方如何应用这些资源声明。详情请参阅[资源](/tasks/resources)。

## 操作系统 {#operating-system}

`[environment].os` 可设为 `"linux"`（默认值）或 `"windows"`。有关 Windows 支持情况，请参阅[智能体能力](/agents/pre-integrated-agents#agent-capabilities)。
