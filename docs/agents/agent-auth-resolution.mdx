## 模型名称解析 {#model-name-parsing}

Harbor（智能体评测框架）会在设置期间使用 LiteLLM（统一模型调用库） 解析模型标识。**所有智能体都应使用相同的 LiteLLM 模型标识**。

浏览 [Harbor 模型查询](https://harbortoolkit.com/model?model=openai%2Fgpt-6-sol)，或在下方输入模型名称，查看其提供方和解析后的模型名称。

<ModelLookup endpoint="https://harbortoolkit.com/resolve" />

<Note>
- **输入模型 (`-m`)** → 你提供的原始模型名称。
- **解析后的提供方** → 用于选择 Harbor 内置的凭据和端点映射。
- **解析后的模型 ID** → 通常会发送给推理提供方；适配器可能会对其进行转换。
</Note>

试用 `openai/gpt-6-sol`、`openrouter/openai/gpt-6-sol`、
`anthropic/claude-sonnet-5-5`、`deepseek/deepseek-v4-flash` 或
`fireworks_ai/accounts/my-account/models/my-custom-model`。

LiteLLM 无法解析的模型标识会直接传递给智能体。之后，各智能体适配器可以根据模型标识推断提供方。

## 自动收集密钥 {#automatic-secret-collection}

对于已识别的[提供方](https://harbortoolkit.com/model?model=openai%2Fgpt-6-sol)和内置[智能体](https://harbortoolkit.com/agent?agent=codex)，Harbor 支持从主机环境变量中自动收集密钥。此行为因智能体和提供方而异，不相关的主机变量不会被转发。

请查看智能体的[身份验证设置](#inspecting-agent-auth-settings)。

## 自动路由密钥 {#automatic-secret-routing}

对于内置智能体，Harbor 会自动将模型提供方的密钥映射到智能体所需的 API 密钥变量名称。因此，即使 Codex（OpenAI 编程智能体） 读取的是 `OPENAI_API_KEY`，你仍可以使用 `OPENROUTER_API_KEY`；Harbor 会替你完成名称映射。

例如，使用 OpenRouter（模型服务聚合平台） 和 Codex 时，**Codex 只会从** `OPENAI_API_KEY` 读取 API 密钥。Harbor 会将 `OPENROUTER_API_KEY` 的值赋给 `OPENAI_API_KEY`，以便 Codex 使用 OpenRouter 进行身份验证。

这样你就可以在多个智能体之间共用一个提供方密钥（例如 `OPENROUTER_API_KEY`），无需了解每个智能体原生的凭据变量名称。这对于使用相同模型和提供方比较不同智能体的基准测试尤其有用。

## 自动密钥路由规则 {#automatic-secret-routing-rules}

<Tip>
**建议先使用 `--dry-run`。**你无需了解所有路由规则；该命令会显示解析后的凭据、端点、模型和 API 格式。
</Tip>

如果提供了多个与提供方或智能体匹配的密钥，Harbor 会根据以下优先级规则确定使用哪个密钥。

1. `--api-key-name ENV_VAR_NAME`
2. `--agent-env ENV_VAR_NAME` 与解析后的模型标识提供方匹配
3. `--agent-env ENV_VAR_NAME` 与所选智能体声明的默认变量匹配
4. 与解析后的模型标识提供方匹配的主机环境变量
5. 与所选智能体声明的提供方匹配的主机环境变量

运行 `harbor run --dry-run`，查看按优先级选中的变量。

</Note>

基础 URL 环境变量的注入遵循与凭据相同的选择和路由规则。

## 高级用法 {#advanced}

### 解析和凭据映射的内部流程 {#parsing-and-credential-mapping-under-the-hood}

LiteLLM 会将模型名称拆分为提供方和模型 ID。随后 Harbor 会在 `PROVIDERS` 中查找该提供方，并将其凭据和端点候选项与智能体声明的回退项及任何显式覆盖项合并。如果解析未能识别提供方，Harbor 就会使用智能体的 `default_provider`。

应用优先级规则后，Harbor 会将选中的凭据值写入智能体声明的目标变量。在此 Codex 示例中，`OPENROUTER_API_KEY` 的值会注入为 `OPENAI_API_KEY`。

### 跳过模型解析和凭据映射 {#skipping-model-parsing-and-credential-mapping}

在某些情况下（例如托管本地模型），可能需要跳过模型名称解析及后续的凭据映射。可在 `harbor run` 命令中使用 `--skip-model-parsing-and-provider-mapping`（或 `--sm`）实现此操作。

使用 `--skip-model-parsing-and-provider-mapping` 时，Harbor 会原样保留模型名称，并使用 `harbor-skip-parsing` 作为提供方标记。上图中红色步骤（LiteLLM 解析和提供方映射）将被跳过。智能体声明的回退项、显式覆盖项、优先级规则和凭据注入仍然生效。

在此示例中，`--api-key-name CUSTOM_KEY` 会选中 `CUSTOM_KEY` 的值，并将其作为 `OPENAI_API_KEY` 传给 Codex。跳过解析不会禁用最后的注入步骤。

### 选择 API 格式 {#selecting-api-formats}

API 格式定义智能体与模型提供方通信的方式。Claude Code（Anthropic 编程智能体） 仅支持 Anthropic Messages（Anthropic 消息接口），而 Grok Build（编程智能体） 等智能体支持多种格式。Harbor 会为 LiteLLM 识别出的提供方选择该智能体的默认格式。

使用 `--api-format` 可覆盖默认格式。可用值包括 `openai_responses`、`openai_chat_completions`、`anthropic_messages`、`google_generate_content` 和 `bedrock_converse`。每个智能体只接受其支持的格式。

### 跨 API 格式路由 {#routing-across-api-formats}

提供方决定 Harbor 从何处查找凭据以及使用哪个端点。智能体选定的 API 格式决定请求的发送方式以及凭据写入哪个变量。即使是同一智能体，这些设置也可能不同。

有些智能体对所有提供方都读取同一个凭据变量；另一些智能体则会根据 API 格式切换变量。Grok Build 就属于后一种：

| 模型提供方 | API 格式 | 凭据路由 |
| --- | --- | --- |
| `anthropic` | Anthropic Messages（Anthropic（模型服务提供商） 消息格式） | `ANTHROPIC_API_KEY` → `ANTHROPIC_API_KEY` |
| `openai` | OpenAI Responses（OpenAI（模型服务提供商） 响应格式） | `OPENAI_API_KEY` → `OPENAI_API_KEY` |
| `openrouter` | OpenAI Chat Completions（OpenAI 聊天补全格式） | `OPENROUTER_API_KEY` → `OPENAI_API_KEY` |

对于 OpenRouter，Grok Build 会读取 `OPENAI_API_KEY` 变量；请求仍会使用 OpenRouter 凭据发送到 OpenRouter。

使用自定义端点时，可通过 `--api-format` 选择协议、通过 `--api-key-name` 选择凭据来源，并通过 `--base-url` 选择端点。目标变量仍由智能体决定。

### 本地模型 {#local-models}

本地模型可能需要显式配置路由，以保留模型名称并选择端点和凭据。此 Codex 示例假设 vLLM（模型推理服务框架） 服务器支持 Responses 和工具调用，并将模型部署在 `/dev/shm/my-model`：

```bash
export VLLM_API_KEY="dummy"
harbor run \
  -t hello-world/hello-world \
  -a codex \
  -m /dev/shm/my-model \
  --skip-model-parsing-and-provider-mapping \
  --api-key-name VLLM_API_KEY \
  --base-url http://host.docker.internal:8000/v1
```

vLLM 默认不要求身份验证；如果启用了 `--api-key`，请将 `VLLM_API_KEY` 设置为对应值。请将 URL 替换为从智能体环境可访问的服务器地址。在 macOS（苹果桌面操作系统） 上，Docker（容器平台） 中的 `host.docker.internal` 可访问主机；智能体容器内的 `localhost` 则指向其自身容器。
