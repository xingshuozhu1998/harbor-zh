Harbor 欢迎社区参与贡献。本指南介绍 Harbor 如何管理 Issue（问题报告）和 PR（合并请求），以及如何提高贡献被接受的可能性。

# 黄金准则 {#golden-rule}

我们采用了 [Ghostty 的黄金准则](https://github.com/ghostty-org/ghostty/blob/main/CONTRIBUTING.md)：**你必须理解自己贡献的代码**。你可以充分使用编程智能体，但需要负责证明自己理解所提交的代码。

证明你理解代码的方式：

- 自行撰写 PR 描述
- 记录设计过程，包括采用的方法和权衡
- 提交整洁且抽象合理的代码（若不严格指导，编程智能体通常不会做到这一点）
- 说明使用了哪些智能体，以及使用程度

随着模型能力提升，我们可能会放宽这一要求。理想情况下，我们可以信任智能体而无需亲自理解代码；但根据我们的经验，目前还做不到。

# 沟通 {#communication}

代码可以由智能体编写。文档、PR 描述、Issue 和评论应由人类在 AI 辅助下撰写。

书面沟通的一般准则是：**初稿和最终稿由你负责，中间过程可以使用智能体协助**。

# Issue {#issues}

Issue 用于报告错误和请求新功能。

遵循我们的沟通标准，请自行撰写 Issue 描述的初稿和最终稿，中间过程可以使用智能体协助。

你必须理解*问题本身*，但无需提出解决方案。如今实现代码比以往容易，因此很多时候提交 Issue 比提交 PR 更合适。

# PR {#prs}

## 智能体、沙箱和插件 {#agents%2C-sandboxes%2C-and-plugins}

我们对集成持较开放态度。唯一要求是至少有一位*用户*提出过该集成需求，请提供相应证据（例如让用户留下评论）。

对于插件，我们的态度略为谨慎，只计划维护需求量较高的插件。

## 接口与核心逻辑 {#interfaces-and-core-logic}

在讨论设计之前，我们通常不会更改接口或核心逻辑；Harbor 格式尤其如此。

如需发起设计讨论，请创建包含 RFC（征求意见稿）的 PR。RFC 应当**简洁**，并由人类在 AI 辅助下撰写。如果 RFC 内容敷衍，我们会关闭该 PR。

RFC 应放在 `rfcs/` 目录下，并遵循现有命名约定。

# CHANGELOG.md {#changelog-md}

对于**重大功能**或**破坏性变更**，请在 `CHANGELOG.md` 的 **Unreleased** 下添加一条简短说明。其他情况无需修改该文件。
